# Поиск нарушений кассира на видео

Решение команды для **ForteBank Datathon 26**. Загружаете запись кассы (`.mov`) — через 1–3 минуты получаете
вердикт, тип нарушения, секунду, 1–3 кадра-доказательства и пункт постановления НБРК, который нарушен.
Анализ полностью локальный: **Qwen3-VL-8B-Instruct** на одном GPU, без облачных AI-сервисов.

## Для жюри

| | |
|---|---|
| Интерфейс | https://v3ljfap04rrur9-8000.proxy.runpod.net — открыт без пароля |
| API | `https://v3ljfap04rrur9-8000.proxy.runpod.net/api/v1`, заголовок `X-API-Key` (ключ передан отдельно) |

```bash
curl -X POST https://v3ljfap04rrur9-8000.proxy.runpod.net/api/v1/analyze -H "X-API-Key: $KEY" -F "file=@video.mov"
# 202 {"job_id": "…"}
curl https://v3ljfap04rrur9-8000.proxy.runpod.net/api/v1/jobs/<job_id> -H "X-API-Key: $KEY"
# processing → done: {"verdict": "violation", "violations": [{"type", "timecode_sec", "description", "evidence_frames"}]}
```

Ответ строго по схеме ТЗ (раздел 10): `type` — название нарушения, `timecode_sec`, `description` — что видно и почему
это нарушение со ссылкой на пункт, `evidence_frames` — 1–3 JPEG в base64 (весь кадр и увеличение). Ошибки: 401 ключ,
404 job_id, 413 размер, 415 не `.mov`, 429 очередь, 503 модель не готова; превышение 5 минут — `failed`.

> Прокси RunPod отклоняет запросы без обычного `User-Agent` (например, голый Python `urllib`). curl, `requests` и
> браузер работают. Если адрес изменится (переезд пода), актуальный указан в форме сдачи.

В интерфейсе: перетащить видео → виден этап анализа → плеер с таймлайном, где нарушение отмечено красным
(клик — переход к моменту), краткое обоснование и ссылка на норму.

## Как это работает

Главный принцип: **модель описывает, код решает.** Большинство нарушений — это *отсутствие* действия
(не пересчитала, не заперла, не проверила документ), а отсутствие нельзя увидеть на кадре. Поэтому модель
только фиксирует факты с секундами, а код ищет пропущенный шаг между ними.

```
видео ─► 1 рамка действия ─► 2 обзор: факты ─► 3 окна рук ─► 4 точечные проверки ─► 5 правила ─► 6 ответ
```

1. **Рамка действия.** По карте движения находится область, где что-то происходит; пустой пол и передний план
   отрезаются (~50% кадра), вспышки света игнорируются.
2. **Обзор.** Модель смотрит всю запись (≈1 кадр/с) и записывает факты с секундами: приход и уход клиентов и
   кассира, сумка, сейф, состояние стола при уходе. Нарушения на этом шаге не оцениваются.
3. **Окна рук.** Всплески движения над столом → окна по 5 с, область движения вырезается из оригинала,
   увеличивается до ~250 тыс. пикселей и смотрится при 6 кадрах/с с узкими вопросами (пересчёт, передача денег, документ).
4. **Точечные проверки.** Каждый факт обзора перепроверяется увеличенным фрагментом в нужный момент; положение
   сейфа, ноутбука, стола модель находит сама (рамка на сетке 0–1000). Любой положительный ответ задаётся второй раз
   на сдвинутом фрагменте; дверь сравнивается «до/после» в одном кадре; наличие инкассаторской сумки подтверждается
   нейтральным вопросом («что передают: деньги / сумку / документы / ничего»).
5. **Правила в коде.** «A и C, а между ними нет B» (сумку вскрыли → деньги в сейфе, пересчёта между ними не было —
   и окна рук этот отрезок покрывали). Невозможное отсекается: нет клиента — нет нарушений пересчёта; нет
   подтверждённой сумки — нет нарушений с сумкой.
6. **Один ответ.** Подтверждённое выше слабого, конкретный тип выше общего; описание из двух предложений с пунктом нормы.

Время: каждое видео получает долю, при которой вся очередь укладывается в 5 минут; при нехватке первыми
пропускаются необязательные проверки. Подробно — [docs/NMK_ENGINE.md](docs/NMK_ENGINE.md).

**Почему не дообучение.** 22 ролика с нарушениями на 18 типов — 1–3 примера на тип: дообучение запомнило бы ролики,
а не нарушения, и не научило бы видеть отсутствие действия. Логика поверх фактов переносится на новые ролики,
объяснима и не требует данных для обучения.

## Качество на обучающих роликах

Разметка — наша, по 42 роликам (22 с нарушением, 20 без). Разметка используется только для оценки, не в анализе.

| Версия | Роликов | Верный тип | Чистые ролики без ложной тревоги |
|---|---|---|---|
| v7, полный прогон | 42 | 10 из 22 | 14 из 20 |
| v9, часть набора | 17 | 7 из 9 | 3 из 8 |

v9 сознательно настроена на полноту (организаторы: пропуск хуже ложной тревоги), поэтому слабые находки
сохраняются и дают ложные тревоги на части чистых роликов. Исправления после v9 (роли кассира и клиента,
нейтральная проверка сумки) проверены точечно, без полного перепрогона. Время: 80–150 с на видео;
5 одновременных видео — все в пределах 5 минут (51–281 с).

## Ограничения и известные ошибки

- Мелкие объекты при низком разрешении: ключ в замке, отдельная купюра, возврат пары купюр клиенту (X-1).
- Направление передачи денег: клиент, кладущий деньги на стол, может быть принят за возврат денег клиенту (X-39).
- Дверь, открытая уже в первом кадре, проверяется хуже — нет кадра «до» (X-33).
- Проверка подлинности купюр на детекторе часто не видна (X-44).
- Нарушения, требующие невидимых данных (проводки, сверка, регистрация в системе), не оцениваются.
- Результат — подсказка проверяющему, не юридическое заключение. Лица не распознаются.

## Запуск на своём GPU

Нужен Linux и NVIDIA GPU с ≥ 20 ГБ памяти (проверено на RTX A5000 24 ГБ); на меньших — `CASH_NMK_PRECISION=4bit`.

```bash
pip install -e '.[nmk]'
huggingface-cli download Qwen/Qwen3-VL-8B-Instruct --local-dir /root/models/Qwen3-VL-8B-Instruct
python scripts/init_env.py                      # создаёт .env с CASH_API_KEY и CASH_UI_PASSWORD
cd frontend && npm ci && npm run build && cd ..
scripts/nmk/run_service.sh                      # сервис на 0.0.0.0:8000
curl -s 127.0.0.1:8000/health/ready             # {"ready": true} после загрузки весов (~1 мин)
```

После загрузки весов интернет не нужен (`HF_HUB_OFFLINE=1`).
